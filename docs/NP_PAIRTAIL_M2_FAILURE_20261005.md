## 为什么慢，以及为什么失败

这次训练约在作业第 4368 秒开始。约 73 分钟用于候选规范化、来源处理、缓存和目标构建，9 个完整训练轮次加第 10 轮部分约用了 20 分钟。可见吞吐为每轮约 2 分钟；GPU 没有发生显存耗尽。主要耗时是 CPU 化学规范化和逐身份视图缓存，并非 GPU 算力不足的证据。

代码曾将 `GradScaler` 缩小 scale 的一次跳步直接视为整次训练失败。PyTorch 的 AMP 流程本来就会在非有限梯度时跳过更新，避免污染权重；跳步本身不能证明之前的已保存权重已经变成非有限值。[PyTorch 官方 AMP 示例](https://docs.pytorch.org/docs/2.14/notes/amp_examples.html)

本轮日志中的 loss 在已完成各轮均有限，开发 BCE 持续下降。不过，未加载实际权重逐张量验证，不能仅据此证明 checkpoint 完全无问题，也不能把梯度溢出解释成分子识别性能差或过拟合。尚未计算相对训练位频率常数的 BCE 比较，以及 FPNet 对随机同窗候选的配对排名区间。

## 已修复的工程行为（本地测试通过，未 GPU 重跑）

新增安全重试：在 AMP 已跳过更新且降低 scale 后，重放整个有效 batch 的 FP32 计算，包含梯度累积的早先微批次。保持原样本、dropout 随机状态和学习率；只有确实成功的优化器更新计入更新数。若 FP32 loss、梯度、权重或优化器状态仍有非有限值，则停止。没有通过丢弃困难样本、隐藏跳步或改变模型结构/损失权重来掩盖问题。

本地新增测试验证：多微批次、非等长最终批次、dropout 随机状态、与直接 FP32 更新一致，以及全局随机状态不被额外重试消耗。相关基础、FPNet、包装、动态融合、forward 域门控和摘要导出共 **29 项测试通过**。另外验证了有限 loss 但非有限梯度时，在更新权重前拒绝继续。今后的完整轮次 checkpoint 会保存 CPU/CUDA 随机状态；本次旧 checkpoint 没有这些字段。这不是 GPU 数值稳定性验证，修复尚未执行正式 Kaggle 运行。

## 为什么本轮不发布

冻结 PRD FR-11 要求“三 seed 均完成至少 6 epochs，无 NaN/Inf”，并要求三种子集成 BCE 和同窗排名门槛。当前只完成第一种子部分训练，所以 M2 不能进入确认性模型选择。独立验收仍保持封存，不能拿单种子开发指标替代独立验收。

累计实际 Kaggle 作业时间为 2082.0 + 29.1 + 2656.4 + 209.3 + 5551.3 = **10528.1 秒**，约 2 小时 55 分钟。原 14400 秒研究预算只余 **3871.9 秒（约 64.5 分钟）**。机器流水线累计计时为 10435.672 秒，较实际作业和少计了启动、封装等开销；后续应以更保守的实际作业累计数计费，不重置计时。剩余时间还需覆盖其余种子、同窗排名、ranker、候选增量和独立验收，不能宣称原预算内已经可以完成发布。

M0 的外部 forward 权重完整训练身份、能量单位与兼容性审查也仍未全部完成，这些模型未进入确认性系统。继续扩大完整训练或提交未验收模型会违背本轮发布要求。

## 下次执行必须改变的工程顺序

1. 直接挂载本次失败作业保留的候选资产和训练/开发缓存，验证文件 SHA、源冻结版本、预处理、身份列表和视图布局；不能再次支付约 73 分钟冷准备。
2. 加载最后完整 epoch 的模型、优化器和 scaler 状态，校验种子、轮次及实际更新数。未完成第 10 轮的梯度不得混入恢复状态。精确恢复还需保留/核验 CPU 与每张 CUDA 的随机状态；目前旧 checkpoint 未保存这些状态，不能声称能够逐位复现连续训练。必要时将恢复标注为新的工程修复实验，而非无缝续训。
3. 在真实 GPU 上先做 bounded 数值稳定性检查；确认 FP32 重试会恢复整批且不改变优化器计数。旧失败记录永久保留。
4. 重新核算本轮剩余预算与后续阶段。需要新的完整研究预算时，以独立的实验清单记录，不把旧计算成本抹掉。
5. 保持拆分盐、身份定义、候选窗、科学参数及独立验收门槛。仅在全部条件满足后生成动态 ID 的推理包并实际提交比赛。
